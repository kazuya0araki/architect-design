# 実行基盤と併用ソフトウェア

AWS・Google Cloud・Azure等のクラウド機能を使う図では、サービス名だけで処理内容が分からない場合、そこに付随する実行エンジン・フレームワーク・ツール・データ形式も反映する。クラウドの製品アイコンだけで、実際に使うAirflowやdbt等を省略しない。

## 何を反映するか

| 関係 | 表示例 | 判断 |
| --- | --- | --- |
| マネージドサービスが提供するエンジン | Cloud Composer + Apache Airflow、Amazon MWAA + Apache Airflow | 対象サービス・版の公式仕様で確認する |
| 利用者が選択して実行するツール | Cloud Run上のdbt、コンテナ上の独自処理 | 実装・設定・ユーザー指定で確認できた場合のみ追加する |
| 処理のフレームワーク | Dataflowで実行するApache Beamパイプライン | 対象パイプラインの実装・公式仕様を確認する |
| データの形式 | 保存層内のApache Icebergテーブル | 利用が確認できた場合に保存層へ表示し、実行エンジンとして描かない |

サービスが対応していることは、その案件で採用している根拠にはならない。Cloud Runからdbt、EMRから特定の処理エンジン、クエリサービスからIcebergの採用を自動的に推定しない。未確認は付随Markdownに記録する。架空の提案では、採用する組み合わせを提案として明記する。

## 配置とモデル

- 同じ処理を実行する基盤とツールは1ノードにする。`icons`に双方の公式素材を並べ、`name`はクラウドサービス名、`role`にツール名と役割を明記する。ツール名をアイコンだけで伝えない。
- 例：`name: Cloud Run`、`role: dbtによる変換`、`icons: [{asset: Cloud Runのパス}, {asset: dbtのパス}]`。異なる工程へ分解したり、基盤からツールへ架空のデータ矢印を追加したりしない。
- ソフトウェアが独立した実体として通信・処理する場合は、実構成どおり別ノードにする。
- Iceberg等の形式は保存層の名前・役割または内側の論理層へ反映する。クラウドサービス全体をその形式のロゴへ置き換えない。
- データ基盤を1要素へ集約するcontext図では、内部ツールはpipeline/detail図と付随説明へ記録する。処理構成を展開する図では、処理の理解に必要な併用ツールを省略しない。
- オーケストレーションは対象の下部へ配置する。Airflowを追記しても、Composer等の所属プロジェクトと制御範囲を維持する。

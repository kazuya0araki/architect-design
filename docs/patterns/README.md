# 構成パターンの選択

左から「データソース → 取り込み → 保存・加工 → 提供・活用」と配置する。保存・加工は必要に応じてRaw、Warehouse、Martなどに分ける。これらの層名は案件の定義に合わせ、層を埋めるためだけのサービスは追加しない。

オーケストレーション、品質、カタログ、監視、アクセス管理、IaCは横断機能として主経路の下に置く。管理対象が確認できる場合だけ制御線で接続する。

目的に応じて以下のパターンを選ぶ。特定の製品や層数を必須にせず、案件で確認できた構成と責務を表す。

| パターン | 図で表現すること | 適用判断 |
| --- | --- | --- |
| 段階的な変換 | 取り込み、加工、提供を分け、保存層内の論理層も必要に応じて示す | 処理責務や変換段階を説明したい |
| 用途別の基盤 | プロダクト用と業務分析用を並行するレーンに分ける | 利用目的、利用者、責務が異なる |
| 契約による境界 | ソースと分析側の間にインターフェースと責任境界を示す | スキーマ変更の影響や所有権を説明したい |
| データ・AI基盤 | 共通の保存・加工からBI、AI、業務システムへの経路を分岐する | 分析以外の活用やReverse ETLも対象になる |

レーンは用途、名前付きの枠は機能のまとまり・所属・責任、ノードは処理・製品・論理データ、矢印は接続を表す。同じ図でレーンの意味を用途と環境に混在させない。現状と将来像は原則として別の図にする。
